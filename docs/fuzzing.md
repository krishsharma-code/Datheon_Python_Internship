# Fuzz testing — Day 18

Day 17 proved *properties* over well-formed input. Day 18 asks the opposite
question: what happens when the input is not well-formed at all?

The plan's definition of done is a single sentence — *random and malformed
input to the CLIs, loaders and chatbot, with zero unhandled exceptions* — so
this document exists to make that sentence checkable: what was fuzzed, how the
corpus is built, what "crash" means here, what the campaign found, and how to
re-run it.

---

## 1. The claim, measured

```
python tools/fuzz.py                  # 400 cases, 16 targets, 0 crashes
python tools/fuzz.py --cases 40       # 640 cases, 16 targets, 0 crashes
python tools/fuzz.py --kind loader --cases 300   # 1,500 mutated datasets
```

Every campaign ends with the same line:

```
No unhandled exceptions: every case stayed inside the CLI contract.
```

The exit code is the verdict: `0` clean, `1` a crash, `2` a misuse of the
driver. That is what makes the campaign usable as a CI step rather than a
report nobody reads.

## 2. What is fuzzed

| Campaign | Target | Surface exercised |
| --- | --- | --- |
| `argv` | `hangman`, `portfolio`, `organizer`, `assistant`, `inventory` | `argparse` configuration, option precedence, validation, the interactive loops |
| `dataset` | `hangman/words-file`, `portfolio/prices`, `portfolio/constituents`, `assistant/intents`, `assistant/faq` | decode → schema check → row parse → error rendering, through `--validate` |
| `loader` | `words`, `prices`, `symbols`, `intents`, `faq` | the loader entry points directly, so a converted error is visible as converted |
| `text` | `chatbot` | `validators.validate_message` and `IntentEngine.respond` over hostile unicode |

The CLI campaigns run the entry points as **real subprocesses**, because that is
the only place a traceback becomes visible to a user. The loader and text
campaigns run **in-process**, because a subprocess would hide the exception
behind `run_cli`'s exit-code mapping — and the point there is precisely whether
the layer converted the failure or leaked it.

## 3. How the corpus is built

`fuzzing.generate_cases(kind, target, seed, count)` is a pure function. Case
*n* is generated by a `random.Random` seeded with `seed * 1000 + n`, so:

- the same coordinates always produce the same corpus;
- case 7 is case 7 whether you asked for eight cases or eight hundred;
- a failure reported as `seed=18018` is reproducible with one integer and no
  attached fixture.

Three shapes are generated:

**`argv`** — a vector of 0–6 tokens. Most come from `fuzzing.ARGV_TOKENS`, a
pool mixing real flags, boundary values (`-1`, `0`, `999999999999999999999`,
`nan`, `inf`), and shapes that break parsers (empty string, `-`, `--`, `---`,
NUL byte, a 300-character token). Roughly one token in six is fuzzed text, so
malformed *content* is covered as well as malformed *structure*. Absolute paths
are deliberately absent from the pool — see §6.

**`bytes`** — either pure noise, or a byte-level mutation of a *real* dataset.
Random noise almost always dies in the decoder; starting from a file the tool
accepts and then breaking one thing is what gets past the encoding check and
into the row, schema and field validators behind it. `mutate_bytes` applies
1–6 edits from a vocabulary that mirrors the defects the loaders already claim
to survive: delete a slice, insert noise, flip a byte, duplicate a row,
truncate, prepend a BOM, translate LF to CRLF, append junk. Half of all
mutations keep the file's opening bytes intact, which is what keeps the
campaign from testing only the decoder.

**`text`** — 1–8 fragments from `fuzzing.TEXT_FRAGMENTS`, sometimes cut
mid-fragment to produce broken grapheme clusters: control characters, ANSI
escapes, a bidi override, a combining accent, emoji, CJK, `%s`, `{0}`,
`__import__('os')`, `; rm -rf /`, `1e309`, `NaN`, a UTF-8 BOM inside a string.

## 4. What counts as a crash

Two judges, both in `fuzzing.py`, and both return a `Verdict` rather than
raising:

- `judge_process` — the exit code must be one of `0`, `1`, `2` (the Day 3
  contract), and neither stream may contain `Traceback (most recent call last)`
  or `During handling of the above exception`. A tool that prints a traceback
  *and* exits 1 is still a failure.
- `judge_exception` — used in-process. The tolerance is a parameter, because
  the layers have different licences:
  - a **CLI** may raise anything in `TOLERATED_EXCEPTIONS` — `DatheonError`,
    `ValueError`, `OSError`, `SystemExit`, `KeyboardInterrupt` — because
    `run_cli` converts all of them into an exit code;
  - a **loader** gets `(DatheonError,)` and nothing else. A `UnicodeDecodeError`
    or an `re.error` escaping a loader is a traceback at the user's terminal,
    which is exactly what Day 7's taxonomy exists to prevent.

One case is reported as *skipped* rather than passed or failed: an argument
vector containing a NUL byte. No kernel will accept a NUL in `argv`, so the case
cannot cross a process boundary. The in-process suite still runs it, because
`main(argv)` takes any string.

## 5. What the campaign found

Two real defects, both in the intent loader, both now fixed and pinned by
regression tests.

**An invalid regular expression escaped as a bare `re.error`.** A mutated
`intents.json` produced the pattern `(unclosed`; `Intent.from_dict` compiled it
without a guard, and the exception travelled past `_parse_intents`' `except
ValueError` (a `re.error` is not a `ValueError`), past `run_cli`, and out to the
terminal as a traceback. The dataset was wrong; the program should have said so
in the taxonomy's language. `Intent.from_dict` now compiles each pattern inside
a guard and raises `ValidationError` naming the intent, the pattern and a hint,
which `_parse_intents` records as a row error with its `intents[i]` index.

**A non-integer `priority` raised an uncaught `TypeError`.** `int()` on a JSON
object raises `TypeError`, which the same `except ValueError` did not catch.
The conversion is now guarded and reported the same way.

Neither was reachable from the examples in `intents.json` or from any test
written by hand. Both were one byte-mutation away from a file the tool loads
happily — which is the argument for this day existing.

## 6. Non-destructiveness

A fuzzer that can point a tool at `/` is a fuzzer that can delete a home
directory. Four rules keep the campaign safe:

1. **No absolute paths in the pool.** No token in `ARGV_TOKENS` starts with `/`
   except `/dev/null` (a read that yields nothing and a write that discards).
2. **The organizer always gets `--dry-run`.** `tools/fuzz.py`'s `_harden`
   injects it when the case does not carry it, so a fuzzed directory argument is
   only ever previewed. The test suite does the same.
3. **Every subprocess runs inside a temporary sandbox** that is also its working
   directory, so relative writes land there and are removed with it.
4. **Log output is redirected.** `DATHEON_LOG_DIR` points into the sandbox, so
   `--log-level DEBUG` never writes a rotating log into the repository.

## 7. Running it

```bash
python tools/fuzz.py                              # all campaigns, seed 18, 25 cases each
python tools/fuzz.py --cases 100 --seed 7         # a deeper, different run
python tools/fuzz.py --kind argv --json           # one campaign, machine-readable
python tools/fuzz.py --timeout 5                  # tighter ceiling per subprocess
python -m pytest tests/test_fuzzing.py -q         # the same corpus, asserted in CI
```

The pytest module is the gate; the driver is the deep run. Both judge through
the same functions, so a case that passes in one is the same assertion as in the
other — that shared verdict is what stops the two from drifting apart.

## 8. Complexity

- One generated case costs one `random.Random` construction and O(size of the
  payload) — microseconds. The corpus is never stored.
- `mutate_bytes` is O(len(base)) per edit, at most six edits, so one case is
  linear in the dataset.
- The `loader` and `text` campaigns are in-process and dominated by file I/O:
  1,500 loader cases run in a few seconds.
- The `argv` and `dataset` campaigns pay one interpreter start per case, about
  0.15 s each. The default 400-case run takes roughly two minutes; CI uses a
  smaller corpus on purpose (see `.github/workflows/ci.yml`).
- Memory is bounded: the driver holds one `Verdict` per case (a few hundred
  bytes), never the payloads.

## 9. Limits

Fuzzing finds crashes, not wrong answers. A tool that answers "0" to every
question passes this campaign and fails Day 17's properties — which is why the
two days sit next to each other. The corpus is also seeded and finite: it is a
regression net over a fixed sample of hostile input, not a proof, and a new seed
is cheap enough to run whenever a loader or a parser changes.
