# Benchmark regression gate — timings that can fail a build (Day 30)

**Harness:** `benchmarks/bench_core.py` · **Gate:** `tools/benchmark_budget.py`
**Budget:** `benchmarks/budget.json` · **CI step:** *Compare against the committed budget*

Day 12 answered *where does the time go* with a profile, and Day 14 wrote the
numbers down. Neither of those can fail a build. A change that doubles the cost
of parsing the S&P 500 constituents table produces a slower figure in a report
nobody re-reads, and every check stays green.

Day 30 closes that gap: the same hot paths are timed on every pull request that
touches them, and each median is compared against a committed ceiling. A
benchmark without a comparison is a table, not a gate.

---

## 1. What is timed

`benchmarks/bench_core.py` times **complete calls of the public API** — never a
re-implementation of it, because a benchmark that drifts from the code measures
a program nobody runs:

| Benchmark | The user-facing cost it stands for |
| --- | --- |
| `bench_calibration` | nothing — it is the machine's speedometer (see §2) |
| `bench_word_list_cold` | the first `hangman` run: read, sanitise and de-duplicate 9,894 words |
| `bench_word_list_cached` | every run after the first: a cache hit and its defensive copy |
| `bench_constituents_parse` | `portfolio` parsing the 500-row constituents table |
| `bench_validator_batch` | 200 tickers through `validators.validate_symbol` |
| `bench_cache_lookup` | 1,000 hits against a warm `caching.DatasetCache` |
| `bench_atomic_write_json` | one save: temp file, `fsync`, `os.replace` |
| `bench_catalogue_lookup` | one catalogue lookup per error code |

The suite is deliberately **outside `testpaths`** in `pyproject.toml`: a bare
`pytest` runs the hermetic correctness suite, and `pytest benchmarks/` runs the
timings. A timing can never fail a correctness run, and a correctness run is
never slowed down by one. The benchmark modules are named `bench_*.py` and
`python_files` collects that pattern only when the directory is named.

## 2. Machine variance, normalised rather than ignored

Absolute microseconds mean different things on a laptop, a shared CI runner and
a container. Comparing raw numbers would either fail honest runs or excuse
dishonest ones.

So the budget stores every ceiling **next to a calibration median**, and the gate
scales each ceiling by how fast this machine is:

```text
factor  = this run's bench_calibration  /  budget's calibration_us
ceiling = max_median_us * factor * (1 + tolerance)
```

`bench_calibration` is a pure-arithmetic loop: no file, no clock, no allocation
pattern any other benchmark touches, so its cost tracks the interpreter and the
processor. The factor is clamped to **0.25×–4×**; outside that band the machine
is not comparable to the one the budget came from, and the run says so on
`stderr` instead of pretending the verdict is exact.

**The honest limitation:** the calibration measures *CPU* speed, while three of
the benchmarks are dominated by *I/O*. Normalising a file read by a CPU loop is
an approximation, which is why every ceiling carries a **2× headroom** on top of
it. The gate is tuned to catch the change that doubles a cost — the one worth a
comment — not to police a 5% drift on a noisy runner.

## 3. The budget file

`benchmarks/budget.json` is generated by the gate itself, never hand-edited:

```json
{
  "schema": 1,
  "recorded": "2026-11-23",
  "python": "3.12.13",
  "headroom": 2.0,
  "tolerance": 0.0,
  "calibration_us": 2801.802,
  "benchmarks": {
    "bench_word_list_cold": { "median_us": 9641.462, "max_median_us": 19282.924 }
  }
}
```

| Field | Meaning |
| --- | --- |
| `median_us` | the median recorded when the budget was cut |
| `max_median_us` | the slowest median still accepted, **before** machine scaling |
| `calibration_us` | the calibration median the ceilings were recorded against |
| `headroom` | the multiplier between a median and its ceiling (2×) |
| `tolerance` | extra slack as a fraction, `0` by default — the headroom is the allowance |

`headroom: 2.0` and `tolerance: 0.0` together are deliberate. The allowance is
visible in the file and in the table; a second, hidden allowance on top of it is
how a gate stops meaning anything.

## 4. Running it

```bash
pytest benchmarks/ -q                                   # just the timings
pytest benchmarks/ --benchmark-json=benchmark-results.json
python tools/benchmark_budget.py --list                 # what am I held to?
python tools/benchmark_budget.py                        # grade the last report
python tools/benchmark_budget.py --json                 # machine-readable verdict
python tools/benchmark_budget.py --results run.json --update   # re-cut the budget
```

Exit codes:

| Code | Meaning |
| --- | --- |
| `0` | every benchmark within its scaled ceiling |
| `1` | at least one finding — a regression, an unbudgeted benchmark, or a budgeted benchmark that did not run |
| `2` | **no verdict**: no report, an unreadable budget, or no calibration sample |

A gate that cannot measure never reports success, which is why `2` exists and
why it is not folded into `1`.

### Findings

| Status | What it means | What to do |
| --- | --- | --- |
| `pass` | within the scaled ceiling | nothing |
| `regression` | over the ceiling by the ratio shown | profile the change, or argue for a new ceiling |
| `unbudgeted` | measured, but the budget names no ceiling | re-cut the budget with `--update` |
| `missing` | budgeted, but not measured in this run | restore the benchmark, or drop its ceiling |

The last two are what keeps the gate honest in both directions: a new benchmark
cannot slip in unprotected, and a deleted one cannot leave a ceiling behind that
quietly measures less each month.

## 5. When the budget is re-cut

A ceiling is a claim about the code as it stands. Re-cut the budget in the same
pull request as an intentional performance change, and say why in the commit
message:

```bash
pytest benchmarks/ --benchmark-json=benchmark-results.json
python tools/benchmark_budget.py --update
git diff benchmarks/budget.json
```

`--update` records each median, writes a ceiling at `median × headroom`, stamps
the date and the interpreter, and stores the calibration. It refuses a run with
no calibration and a run with no benchmarks, because either one would produce a
budget that protects nothing.

## 6. The workflow

`.github/workflows/benchmarks.yml` runs the suite, grades the report, prints the
budget, and uploads `benchmark-results.json` as an artefact. It is kept out of
`ci.yml` on purpose — a timing on a shared runner is a signal about *change*,
not about every commit — and fires:

- on a pull request that touches `benchmarks/`, the gate, or any measured module;
- weekly, on a schedule, so a regression from an untouched dependency still surfaces;
- on demand, with `workflow_dispatch`.

`tests/test_benchmarks.py` audits that workflow: the triggers, `permissions:
contents: read`, the timeout, the gate invocation and the uploaded report. It
also audits the harness itself — every benchmark must take the `benchmark`
fixture, carry a docstring and full annotations, and be covered by a ceiling —
and proves each audit fires on a doctored copy, so the checks are not vacuous.
